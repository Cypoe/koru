# An emitted file that does not name its generator invites the wrong verb (belief)

`koruc` emits a scaffold that is, to a reader, indistinguishable from a
hand-written Zig project: `build.zig`, `build_backend.zig`, `build_output.zig`
starting at `const std = @import("std")`, beside a `.k` source. The obvious
verb in a Zig-shaped directory is `zig build` — and it runs clean, because the
emitted files are valid Zig. What it proves is only that *already-emitted* Zig
still compiles; the compiler is never re-run, and the `.k` source is never
re-checked. A green `zig build` in an emitted scaffold is a vacuous oracle for
"does koruc still accept this" — and nothing on the surface said so.

No refusal can fire: `zig build` is doing exactly what the file invites. The
miss is silent by construction, invisible to the friction corpus (which counts
koruc refusals). The only place the teaching can live is the artifact itself.

## The rule

Every emitted file that invites a host-toolchain verb owes its first line to
its generator: name the emitter, name what the obvious verb actually does, name
the verb that re-checks the source. `emit_build_zig.zig` now opens both build
scripts with:

    // Generated by koruc — `zig build` here recompiles emitted backend.zig, never the Koru source; re-verify: koruc build <file>

The sibling half already existed: `guardNonKoruBuildZig` stops koruc
*writing over* a foreign build.zig
([[frag-koruc-must-not-clobber-foreign-build-zig]]). This is the other
direction of the same ambiguity — the emitted file must also not *pass as*
foreign to the reader.

## Open

`output_emitted.zig`, `backend.zig`, `program.ast.json`, `compiler_env.json`
still carry no generator stamp. The build scripts were the miss surface; whether
the stamp belongs on every emitted artifact is the same question one directory
over.
